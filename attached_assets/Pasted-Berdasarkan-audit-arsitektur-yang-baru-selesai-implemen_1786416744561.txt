Berdasarkan audit arsitektur yang baru selesai, implementasikan Fase B — Unified Order API.

PRIORITAS:
Membuat satu kontrak order kanonik untuk seluruh ecosystem Gustafta tanpa membongkar flow checkout/Scalev yang sudah live.

TARGET:

POST /api/v1/orders

Endpoint harus menggunakan Bearer API key dengan pola security yang sama seperti:

POST /api/v1/ai/assist

Ketentuan:

1. Request menerima:

   * product_id ATAU
   * package_id
   * buyer information minimum yang diperlukan untuk membuat transaksi/payment.
     Jangan mengizinkan keduanya kosong.

2. Order response harus mengembalikan minimal:

   * order_ref
   * product_id jika ada
   * package_id jika ada
   * amount
   * currency
   * status
   * payment_url / checkout_url
   * created_at

3. Tambahkan dukungan package_id ke order model/database secara backward-compatible.
   Jangan merusak order lama.

4. Gunakan Product Registry / Package Registry sebagai source of truth.
   Jangan membaca pricing.ts frontend sebagai sumber harga.

5. Validasi:

   * product/package harus ACTIVE dan purchasable.
   * harga diambil server-side.
   * client tidak boleh menentukan harga sendiri.
   * package version yang dipakai harus dapat dilacak.
   * order harus menyimpan snapshot/identitas produk yang diperlukan untuk audit.

6. Payment:
   Gunakan Scalev yang sudah LIVE.
   Jangan membuat payment gateway baru.
   Jangan menghidupkan Mayar.
   Jangan mengubah webhook Scalev yang sudah berjalan kecuali benar-benar diperlukan untuk kompatibilitas.

7. Payment URL:
   Gunakan mekanisme checkout Scalev yang saat ini sudah terbukti live.
   Jika payment link per-order belum bisa dibuat secara dinamis, jangan membuat workaround berbahaya.
   Identifikasi keterbatasannya dan implementasikan solusi paling aman yang tetap dapat menghubungkan order ke transaksi Scalev.

8. Security:

   * Bearer API key.
   * fail-closed jika key tidak dikonfigurasi.
   * constant-time comparison jika masih menggunakan static key.
   * jangan expose API key.
   * rate limit endpoint order.
   * jangan log credential atau data sensitif.
   * jangan gunakan /api/store/notify sebagai external contract.

9. Compatibility:

   * Jangan merusak POST /api/store/order yang sudah live.
   * Jangan merusak existing Scalev webhook.
   * Jangan mengubah contract /api/v1/catalog/*.
   * Jangan mengubah /api/v1/ai/assist.
   * Jangan menyentuh Phase 1B/1C/1D Gaia SIAP.

10. Jangan implementasi api_clients registry atau outbound webhook pada task ini.
    Itu Phase berikutnya.

11. Jangan melakukan cleanup besar seperti menghapus store_products, pricing.ts, agents, atau rename legacy columns.
    Cleanup dilakukan terpisah setelah transaction flow stabil.

TEST WAJIB:

A. valid product_id → order berhasil
B. valid package_id → order berhasil
C. product_id + package_id kosong → 400
D. product/package tidak valid → 4xx
E. inactive product/package → ditolak
F. client mencoba mengirim harga berbeda → harga server tetap digunakan
G. tanpa API key → 401
H. API key salah → 401
I. existing /api/store/order tetap PASS
J. existing Scalev webhook regression tetap PASS
K. existing catalog API regression tetap PASS

SEBELUM IMPLEMENTASI:

Baca terlebih dahulu schema/database, existing order flow, Scalev integration, dan webhook.

Jika ditemukan bahwa Scalev membutuhkan provisioning/variant tertentu agar package dapat dibayar, jangan membuat asumsi. Laporkan blocker teknis tersebut.

Setelah selesai laporkan:

* files changed
* schema migration
* endpoint contract
* contoh request/response
* bagaimana package_id diproses
* bagaimana payment_url dihasilkan
* security changes
* seluruh hasil test
* blocker yang tersisa

SCOPE STRICT: hanya Unified Order API + package support + payment-link connection yang diperlukan.
